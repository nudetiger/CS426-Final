\section{Testing and verification}
\label{sec:testing}

Testing here is deliberately lopsided. Logic that reduces to a function --- parsers, the action
protocol, the layout solver, the backup format --- carries \textbf{125 JUnit tests} that run on the JVM
in seconds with no device. The one thing that can irreversibly destroy a user's library, a database
migration, carries \textbf{2 instrumented tests} against real SQLite. The rest was verified by hand,
and the last subsection says where that leaves holes.

\subsection{The decision that makes the unit suite worth having}

\begin{sloppypar}
These are not smoke tests, because the interesting logic was written so it could be called without an
Android runtime. \code{util/} is plain Java with no \code{android.*} import anywhere:
\code{MarkdownLinkParser} (wiki-links and rename), \code{TreeRules} (move legality),
\code{FtsQueryBuilder}, \code{TextDiff}, \code{ForceLayout} (Fruchterman--Reingold),
\code{StreamingAnswerExtractor}, and \code{ExportJsonWriter}~/ \code{ImportJsonReader}~/
\code{ImportTitles}. \code{ai/protocol/} and \code{ai/engine/KbIndex} depend only on the Room
\emph{entity} data classes and Gson --- never on a DAO, a \code{Context} or a \code{ViewModel} --- so
\code{ActionParser}, \code{ActionValidator}, \code{ActionLabels} and \code{KbIndex} are ordinary
objects a test constructs with a list of \code{Node}s. The language boundary and the test boundary
were drawn in the same place, which is why the validator --- the component standing between a language
model and the database --- is the most heavily tested class in the app rather than the least.
\end{sloppypar}

\subsection{Instrumented tests: Room migrations}

\begin{sloppypar}
\code{MigrationTest} is the only test needing a device, because it needs real SQLite. Room's
\code{MigrationTestHelper} builds an old database from the schemas exported to \code{app/schemas/},
which reach the instrumentation assets through the \code{androidTest.assets.srcDirs} line in
\code{app/build.gradle}. Both tests insert real rows before migrating and assert on them after; an
empty-database migration would prove nothing.
\end{sloppypar}

\begin{itemize}
  \item \code{migrates1To3KeepingPosts} --- v1 predates \code{exportSchema}, so there is no
        \code{1.json} to build from: the test writes the original v1 \code{nodes} table and indices by
        hand, inserts a branch and a post, then opens the result through \code{Room.databaseBuilder}
        with \code{MIGRATION\_1\_2} and \code{MIGRATION\_2\_3}. Opening through Room \emph{is} the
        schema assertion --- Room compares the live schema against v3 and throws on any mismatch. It
        then asserts the post's title, status and favourite flag survived, that \code{posts\_fts} was
        rebuilt \emph{from the existing rows} rather than starting empty (a \code{MATCH 'spring'}
        query finds the pre-existing post), and that the new chat tables exist and are empty.
  \item \code{migrates2To3AddingChatTables} --- builds v2 from \code{2.json} via the helper, inserts a
        post plus a tag and its join row, then runs \code{runMigrationsAndValidate(\dots, 3, true,
        MIGRATION\_2\_3)} so the helper validates the end schema against \code{3.json}, and asserts
        the tag survived and \code{chat\_messages} exists and is empty.
\end{itemize}

The FTS assertion earns its keep: a content-backed FTS4 table added by a migration is empty until it
is explicitly rebuilt, and nothing would have failed loudly --- search would simply have returned
nothing for every post written before the upgrade.

\subsection{Running the suites}

\begin{lstlisting}[language=bash]
gradlew test                       # JVM unit tests - no device, seconds
gradlew connectedDebugAndroidTest  # migrations - needs an emulator or device
\end{lstlisting}

\noindent On Windows both are invoked as \code{.\textbackslash gradlew.bat}.

\subsection{What is not covered}

Three gaps, plainly. There are \textbf{no UI tests}: Espresso sits on the \code{androidTest} classpath
but no fragment, adapter or navigation path has an automated test, so the review-and-apply flow --- the
riskiest screen in the app --- is verified only by hand. There is \textbf{no automated test of the AI
round trip}: it needs a live DeepSeek key and a running gateway, so it is neither hermetic nor free;
the protocol is tested from the parser and validator inwards, and the network edge only through the
frame decoder. And there is \textbf{no tablet-hardware pass}: the above-600\,dp dimension overrides
were checked on a resized emulator, never on real hardware. \S\ref{sec:self} lists these among the
things a next iteration would fix first.
